# 多模型 Review：为什么一个模型不够？

封面图中文提示词：

> 一张公众号科技文章封面图，主题是“多模型 Review：为什么一个模型不够？”。画面中心是一份代码 Diff，周围有多个不同能力的 AI 模型节点从安全、性能、架构、异常处理、长上下文等角度进行交叉审查，右侧汇聚成一份带风险分级和可信度标记的 Review 结果。整体风格现代、工程化、克制，深色科技背景，蓝色和绿色代码流为主，橙色风险信号点缀，不要文字、不要 Logo、不要水印，适合宽幅公众号封面。

上一篇我们讲了 Pre-PR Gate。

它解决的是一个时机问题：

> 不要等代码进入正式 PR 后，才第一次做 AI Review。

但当 AI Review 被前置之后，新的问题马上出现了：

> 用一个模型来审代码，够不够？

很多团队刚开始做 AI Review 时，都会从单模型开始。

这很正常。

接入简单，成本可控，链路也容易解释。给模型一份 diff，再加一段 Review Prompt，让它找问题、打等级、给建议。第一版看起来效果通常还不错，至少能抓出一些命名、异常处理、测试覆盖、日志上下文之类的问题。

但跑一段时间后，就会发现一个很微妙的现象：

> 模型不是完全不行，而是它的盲区很稳定。

它擅长的问题，会反复发现。

它不敏感的问题，也会反复漏掉。

这就是为什么多模型 Review 会成为 Agent 工程化里的关键能力。

不是因为“模型越多越高级”。

而是因为工程 Review 本来就不是一个单视角问题。

## 单模型 Review 的问题：盲区稳定存在

一个模型再强，也会有自己的偏好。

有的模型很擅长代码结构和重构建议，但对业务安全边界不敏感。

有的模型很擅长发现显性的 bug，却容易忽略架构层面的长期风险。

有的模型长上下文能力强，适合读大范围改动和文档，但在局部代码缺陷上不一定最锋利。

有的模型推理能力强，但成本高、速度慢，不适合每一次小改动都调用。

所以单模型 Review 最大的问题，不是“它不聪明”。

而是：

> 它会用同一种能力结构，反复审查所有类型的代码变更。

这在工程上很危险。

因为 Review 的对象并不单一。

一次代码变更里，可能同时包含：

- 业务逻辑调整。
- 数据库访问变化。
- 缓存策略变化。
- 异常处理路径。
- 权限判断。
- 并发边界。
- 日志和监控。
- 测试覆盖。
- 架构分层。

这些问题需要不同视角。

如果只让一个模型看，就像让一个 Reviewer 同时扮演安全专家、性能专家、架构师、测试工程师和业务负责人。

当然可以看。

但很难一直稳定地看好。

多模型 Review 的第一层价值，就是用差异化视角减少稳定盲区。

同一份 diff，让不同模型、不同角色、不同 Skill 去看。

如果多个模型从不同角度命中同一个问题，这个问题的可信度就应该提高。

如果某个问题只被一个模型发现，也不代表它一定不重要，但它更适合进入人工复核或 Judge 汇总。

这就是“交叉审查”的意义。

## 多模型不是堆模型，而是做角色分工

很多人一听多模型，就容易想到：

> 那我是不是同时调三个模型，把结果合并一下就行？

这只是最粗糙的多模型。

真正有价值的多模型 Review，不是把模型数量堆上去，而是把模型变成有职责的角色。

比如在这个项目里，策略不是直接写成“调用 qwen-plus、qwen-max、deepseek-v3”。

更合理的表达是：

```yaml
roles:
  - role: SECURITY_AUDITOR
    model: qwen-max
    skills:
      - SecuritySkill
  - role: PERFORMANCE_ANALYST
    model: qwen-plus
    skills:
      - PerformanceSkill
  - role: EXCEPTION_HANDLER
    model: deepseek-v3
    skills:
      - ExceptionHandlingSkill
  - role: ARCHITECT_REVIEWER
    model: qwen-max
    skills:
      - JavaCodeStyleSkill
      - PerformanceSkill
```

这里的关键不是模型名称。

关键是“角色 + 模型 + Skill”的组合。

角色决定它看什么。

模型决定它有什么能力边界。

Skill 决定它按什么专业方法审查。

同一个模型，可以承担不同角色。

不同模型，也可以承担同一个角色。

真正重要的是：每一次 Review 都应该知道自己为什么调用这个模型，它负责什么，输出要进入哪一种决策链路。

这也是 Agent 工程化和普通 Prompt 调用的区别。

普通调用关注的是：

> 这次问哪个模型？

Agent 策略关注的是：

> 这次变更需要哪些审查角色？每个角色用什么模型？它们的结果如何被聚合和裁决？

## 四类策略：不是所有改动都需要同一种阵容

多模型 Review 不能无脑加重。

否则它会变慢、变贵，也会制造更多噪音。

更合理的做法，是按风险选择策略。

项目里已经有四类很典型的内置策略：

配图中文提示词：

> 一张横向策略分层信息图，主题是“多模型 Review 的策略分层”。画面从左到右展示四个审查强度逐级升高的策略卡片或阶梯：fast-scan 快速自查、cross-check 交叉审查、quality-gate 质量闸门、architecture-board 架构委员会。每一层体现不同风险场景和治理强度：低风险小改动强调快速反馈，中等风险强调多模型互补，正式 PR 前核心链路强调多 Agent 质量门禁，架构调整强调 Worker 先审、Judge 汇总。整体像从轻量到重型的工程治理梯度，箭头向右推进，颜色从蓝色、绿色、黄色到橙红色递进，风格简洁、现代、技术感强，不要 Logo、不要水印，适合公众号正文配图，尽量少文字或不出现文字。

第一类是 `fast-scan`，快速自查。

它适合日常小改动、提交前自检、低风险配置变更。通常用一个成本均衡的模型就够了，重点是快反馈，不追求覆盖所有风险。

第二类是 `cross-check`，多模型交叉审查。

它适合中等风险需求、多人协作代码、需要提高召回率的改动。可以让两个 Worker 模型从不同角度看同一份 diff，比如一个偏规范和性能，一个偏安全和异常处理。

第三类是 `quality-gate`，Pre-PR 质量闸门。

它适合正式 PR 前、核心链路改动、高风险业务需求。这里就不只是多模型，而是多 Agent 角色并行审查，覆盖安全、性能、规范、异常处理和架构风险。

第四类是 `architecture-board`，架构委员会评审。

它适合架构调整、领域模型升级、高影响范围重构。多个 Worker 模型先给出判断，再由 Judge 模型做汇总、冲突识别和二次裁决。

这四类策略背后的逻辑很朴素：

> 低风险变更要快，高风险变更要稳，架构类变更要能处理分歧。

所以，多模型 Review 的重点不是“每次都多调几个模型”。

而是把不同审查强度变成可复用策略。

开发不需要手写 JSON。

团队也不需要每次重新讨论“这次该怎么审”。

选择策略，本质上就是选择这次变更的治理强度。

## 模型档案：先描述能力，再编排策略

如果多模型只是一个模型列表，很快就会失控。

因为团队迟早会遇到这些问题：

- 这个模型适合长上下文还是短 diff？
- 这个模型适合 Judge 还是适合 Worker？
- 这个模型成本高不高？
- 超时时间应该设多少？
- 默认 temperature 应该是多少？
- 它是不是只能在内网使用？
- 它适合安全审查，还是更适合 PR 摘要？

所以模型需要先变成“档案”。

在项目里，`ModelProfile` 大概包含这些信息：

```ts
export interface ModelProfile {
  id: string
  providerId: string
  modelName: string
  displayName: string
  capabilityTags: string[]
  defaultTemperature: number
  timeoutSeconds: number
  enabled: boolean
}
```

这里最值得关注的是 `capabilityTags`。

它不是装饰字段。

它是在告诉策略系统：这个模型适合干什么。

比如：

```json
[
  {
    "profile": "qwen-plus",
    "tags": ["代码审查", "日常质量检查", "成本均衡"]
  },
  {
    "profile": "qwen-max",
    "tags": ["Judge", "架构评审", "复杂推理"]
  },
  {
    "profile": "deepseek-v3",
    "tags": ["交叉审查", "代码理解", "缺陷发现"]
  },
  {
    "profile": "kimi-k2",
    "tags": ["长上下文", "文档理解", "PR 摘要"]
  },
  {
    "profile": "local-coder",
    "tags": ["私有化", "离线审查"]
  }
]
```

有了模型档案，策略才有编排基础。

否则所谓多模型，只是一堆 API Key 和模型名。

配图中文提示词：

> 一张工程架构信息图，主题是“从模型档案到审查策略”。画面从左到右展示四个配置对象如何共同决定一次 Review 执行：ModelProvider 表示供应商、Endpoint 和鉴权方式；ModelProfile 表示具体模型、能力标签、默认参数和超时；RoleBinding 表示审查角色与模型、Skill 的绑定；GatePolicy 表示阻断、复核、建议和严重等级规则。四个对象最终汇聚到下方或右侧的 compiled modelsConfig，形成一次可执行的 Review 策略。整体像平台配置编排图，节点清晰、箭头明确，有“能力标签”“角色绑定”“质量门禁”这类抽象视觉元素。风格现代、工程化、克制，灰蓝背景，蓝色主线箭头，绿色汇聚线，橙色策略信号点缀，不要 Logo、不要水印，适合公众号正文配图，尽量少文字或不出现文字。

这张图里有四个关键对象：

- `ModelProvider`：模型供应商、Endpoint、鉴权方式。
- `ModelProfile`：具体模型、能力标签、默认参数。
- `RoleBinding`：把某个审查角色绑定到某个模型和 Skill。
- `GatePolicy`：决定哪些问题阻断、哪些问题复核、哪些问题建议。

它们最后会被编译成一次可执行的 `modelsConfig`。

也就是说，业务上看到的是“选择质量闸门策略”。

系统里落下去的是一套可执行的多模型编排配置。

## 多模型结果怎么合并？

多模型 Review 还有一个很现实的问题：

> 多个模型说法不一致怎么办？

比如一个模型认为这是 BLOCKER，另一个模型认为只是 MINOR。

一个模型说这里有并发风险，另一个模型没有提。

一个模型建议重构，另一个模型认为当前实现可以接受。

如果只是把所有结果拼在一起，Reviewer 会更累。

所以多模型结果必须聚合。

一个可落地的聚合逻辑可以分成四步：

```yaml
aggregation:
  normalize:
    - "把不同模型输出统一成 Finding"
    - "统一 severity、category、file、line、evidence"
  deduplicate:
    - "合并同一文件同一风险点"
    - "保留不同模型的证据来源"
  score:
    - "交叉命中提高置信度"
    - "高风险类别提高优先级"
    - "缺少证据降低置信度"
  decide:
    - "BLOCKER 进入阻断"
    - "冲突结论进入 Judge 或人工复核"
    - "低置信建议进入 advisory"
```

这里有一个很重要的原则：

> 多模型不是为了制造更多评论，而是为了提高结论质量。

所以输出不应该是：

> 模型 A 说了 10 条，模型 B 说了 8 条，模型 C 说了 12 条。

更好的输出应该是：

> 本次 Review 聚合出 6 个有效 Finding，其中 2 个被多个模型交叉命中，1 个存在模型分歧，3 个为低风险建议。

这才是 Reviewer 能消费的结果。

## 成本、速度和可信度：三者要一起设计

多模型 Review 最大的误区，是只谈准确率。

工程系统不能只看准确率。

它还要看成本、速度、稳定性和可解释性。

一个简单的策略选择表可以是这样：

```yaml
strategySelection:
  smallChange:
    strategy: fast-scan
    goal: "快速反馈"
    maxLatency: "低"
    cost: "低"
  mediumRisk:
    strategy: cross-check
    goal: "提高缺陷召回"
    maxLatency: "中"
    cost: "中"
  highRiskPrePr:
    strategy: quality-gate
    goal: "阻断基础风险"
    maxLatency: "中高"
    cost: "中高"
  architectureChange:
    strategy: architecture-board
    goal: "处理分歧和复杂判断"
    maxLatency: "高"
    cost: "高"
```

这也是为什么多模型能力一定要平台化。

如果每个开发自己决定调哪个模型，团队很快会失去统一标准。

有人为了快，只跑最轻的模型。

有人为了稳，每次都跑最重的组合。

有人把 Judge 当成最终裁判。

有人只看模型评论，不看证据。

最后结果就是：AI Review 看起来很热闹，但治理能力没有沉淀下来。

平台要做的事情，是把策略变成默认路径。

让开发在合适的场景里，用合适的模型组合，得到合适粒度的反馈。

## 多模型治理的本质

多模型 Review 的本质，不是追求一个“永远正确”的模型组合。

它追求的是三个东西。

第一，提高召回率。

不同模型和不同角色互相补位，让更多风险在提交前暴露出来。

第二，提高可信度。

当多个模型从不同角度命中同一问题，系统可以把它标记为更高置信的 Finding。

第三，提高可治理性。

模型不是散乱调用，而是被纳入 Provider、Profile、Strategy、RoleBinding、GatePolicy 这一套结构里。

换句话说：

> 多模型 Review 不是模型能力的简单叠加，而是工程治理结构的升级。

当团队把模型能力标签化、把角色绑定策略化、把输出结果结构化，AI Review 才能从“工具体验”进入“工程基础设施”。

## 结尾

一个模型可以帮我们开始 AI Review。

但如果要把 AI Review 放进团队研发流程里，只靠一个模型通常不够。

因为工程问题天然是多视角的。

安全、性能、异常、架构、测试、业务语义，本来就需要不同能力参与判断。

多模型 Review 的价值，不是让系统看起来更复杂。

它的价值是：

> 用差异化模型能力提高召回率，用角色分工降低噪音，用策略编排把 Review 变成可治理流程。

不过，多模型带来一个新的问题：

当多个模型意见不一致时，谁来汇总？

谁来识别冲突？

谁来判断哪些问题应该阻断，哪些问题应该交给人确认？

这就引出了下一篇：

> Judge Agent：让模型审模型，但不能让模型独裁。
