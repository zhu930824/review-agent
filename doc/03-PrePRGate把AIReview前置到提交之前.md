# Pre-PR Gate：把 AI Review 前置到提交之前

封面图中文提示词：

> 一张公众号科技文章封面图，主题是“Pre-PR Gate：把 AI Review 前置到提交之前”。画面中间是一道发光的质量门禁，左侧是开发分支和 AI 生成代码流，右侧是更清晰、更小体积的 PR 进入人工评审区。画面包含风险分级、通过、阻断、人工复核等抽象视觉元素。整体风格现代、工程化、克制，深色背景，蓝色代码流和橙色风险信号点缀，不要文字、不要 Logo、不要水印，适合宽幅公众号封面。

上一篇我们聊到：AI Coding 之后，Code Review 会成为新的瓶颈。

这句话如果继续往下拆，会看到一个更具体、也更容易被忽略的问题：

> 不是 Review 不重要了，而是 Review 发生得太晚了。

想象一个很常见的下午。

开发上午用 AI 快速完成了一组接口改造，中午补了几个测试，下午创建 PR。Reviewer 打开之后，第一眼看到的不是一个“可以认真讨论设计取舍”的变更，而是一堆基础问题：异常分支没补齐、测试只覆盖 happy path、某个 Service 里混进了 SQL 细节、PR 描述还只写了“fix issue”。

这些问题当然需要被发现。

但它们真的应该等到正式 PR 阶段，才第一次被发现吗？

在传统研发流程里，代码产出速度相对稳定，PR 后置 Review 勉强还能承受。开发写完代码，提交 PR，Reviewer 开始看；发现问题，打回修改；开发再提交，Reviewer 再看。

AI Coding 之后，代码变更的数量、体积和频率都被放大了。如果所有基础问题都堆到正式 PR 阶段才暴露，Reviewer 很快就会被拖进反复返工的协作链路里。

所以新的问题不是“要不要 Review”。

而是：

> Review 应该发生在什么时候？

Pre-PR Gate 的核心思想很简单：

> 不要等代码进入正式 PR 后，才第一次做 AI Review。应该在提交 PR 之前，先让 AI 做一轮质量门禁。

这不是给流程再加一道形式主义的门。

它真正想做的，是把反馈左移。

## 正式 PR 为什么太晚？

正式 PR 有一个隐含前提：

> 这份代码已经到了可以请求别人认真看的阶段。

但现实经常不是这样。

很多 PR 里还混着大量基础问题：

- 明显的异常分支缺失。
- 命名和结构不统一。
- 测试只覆盖 happy path。
- Controller 直接编排复杂业务。
- SQL 或缓存处理有明显风险。
- PR 描述不清楚，Reviewer 需要自己猜改动意图。

这些问题不复杂，但它们非常消耗注意力。

更麻烦的是，PR 一旦发出来，就会进入协作链路。

Reviewer 被通知。

CI 开始跑。

评论开始积累。

开发开始来回修。

每一次返工，都不只是某个人多花了十分钟，而是整个协作链路发生了一次上下文切换。

Pre-PR Gate 想解决的不是“让流程更复杂”。

它想解决的是：

> 在正式占用 Reviewer 时间之前，先把机器能发现的问题过滤掉。

这样正式 PR 进入人工 Review 时，Reviewer 拿到的就不再是一份粗糙 diff，而是一份已经经过基础过滤、带着摘要和风险分级的变更。

这时人的注意力，才更容易放到真正值得判断的地方：

- 这个设计是否符合业务长期演进？
- 这个边界划分是否合理？
- 这个风险是否可以在当前阶段接受？
- 这个改动是否影响了团队约定的架构方向？

这些才是人工 Review 最值钱的部分。

## Pre-PR Gate 到底是什么？

Pre-PR Gate 可以理解成正式 PR 之前的一道质量门。

它不一定要求开发已经创建 PR。只要系统能够拿到当前工作分支和目标分支之间的 diff，就可以提前完成一轮 AI 审查。

一个典型流程是：

配图中文提示词：

> 一张横向流程图，主题是 Pre-PR Gate 主流程。画面从左到右依次表现：选择项目与分支、生成 Diff 上下文、规则扫描、多角色 AI Review、Finding 聚合、风险分级，然后分流到生成 PR Summary 和 Gate 决策；Gate 决策再分成通过、阻断、需要人工复核三种结果。整体像一条清晰的工程流水线，中间有质量门禁和风险分级仪表盘的视觉元素，多角色 AI Review 可以用多个小型 Agent 节点或审查视角图标表示。风格现代、简洁、技术感强，蓝色为主，搭配绿色通过、红色阻断、橙色复核信号，不要 Logo、不要水印，适合作为公众号正文配图。

拆开看，大概包括七步。

第一，选择项目和分支。

开发选择当前开发分支、目标分支，以及要使用的 Review 策略。

第二，生成 Diff 上下文。

系统不只是把 diff 原样丢给模型，而是要补充文件路径、变更类型、相关上下文、历史规则、目录归属等信息。没有上下文的 Review，很容易变成泛泛而谈。

第三，执行规则扫描。

这一步适合处理确定性更强的问题，比如禁止 Controller 直连数据库、禁止明文密钥、禁止绕过统一异常处理、禁止在核心链路里引入不受控的线程池。

第四，执行多角色 AI Review。

比如安全审计 Agent、性能分析 Agent、架构评审 Agent、异常处理 Agent 分别看同一组变更。它们的关注点不同，输出也应该被分层聚合。

第五，聚合 Finding。

AI 的输出不能只是一段自然语言评论，而要变成结构化问题。否则它很难进入后续流程，也很难沉淀为团队资产。

第六，生成 Gate 结果。

根据严重等级，决定通过、阻断，还是需要人工复核。

第七，生成 PR Summary。

当代码通过 Pre-PR 后，系统顺手生成一份高质量 PR 描述，让正式 PR 更容易被 Reviewer 理解。

注意这里有一个关键变化：

> Pre-PR Gate 不是把人工 Review 提前，而是把机器擅长的检查提前。

人依然要看。

但人看的应该是经过整理的、真正值得判断的问题。

## Gate 不是建议列表，而是决策系统

很多 AI Review 工具停在“建议列表”这一层。

模型看完代码，输出几条建议：

> 这里建议补充异常处理。  
> 这里可能存在并发风险。  
> 这里建议增加测试用例。

这当然有价值，但还不够。

如果每一条建议都需要人重新判断要不要处理，AI Review 最终还是会变成新的信息噪音。

Pre-PR Gate 的关键，是把建议变成决策。

也就是回答三个问题：

- 哪些问题必须修？
- 哪些问题需要人确认？
- 哪些问题只是建议？

所以 Gate 里一定要有严重等级。

我更倾向于用四类：

```yaml
severity:
  BLOCKER:
    meaning: "必须阻断"
    examples:
      - "明确安全漏洞"
      - "高概率数据不一致"
      - "核心链路并发风险"
      - "破坏架构硬约束"
  MAJOR:
    meaning: "需要人工复核"
    examples:
      - "重要异常分支缺失"
      - "测试覆盖不足"
      - "架构边界存在争议"
  MINOR:
    meaning: "建议修复"
    examples:
      - "命名不够清晰"
      - "日志上下文不足"
      - "局部可读性问题"
  INFO:
    meaning: "提示和记录"
    examples:
      - "可选优化建议"
      - "后续重构线索"
```

对应的 Gate 决策可以很简单：

配图中文提示词：

> 一张决策树式信息图，主题是 Pre-PR Gate 如何根据 Review Findings 做分流。画面顶部是 Review Findings 汇入口，向下依次判断是否存在 BLOCKER、是否存在 MAJOR、是否只有 MINOR 或 INFO；结果分成三类：BLOCKED 必须修复、NEEDS_HUMAN_REVIEW 人工确认、PASSED 带建议或无风险放行。整体结构像质量门禁的分流控制台，分支清晰、层级明确，BLOCKER 用红色警示，MAJOR 用橙色复核，PASSED 用绿色通过。风格克制、工程化、适合技术文章正文插图，不要 Logo、不要水印，尽量少文字或不出现文字。

如果存在 BLOCKER，就阻断。

如果没有 BLOCKER，但存在 MAJOR，就进入人工复核。

如果只有 MINOR 和 INFO，可以带建议放行。

如果没有风险，直接通过。

这套逻辑看起来朴素，但它非常重要。

因为它避免了两个极端。

一个极端是 AI 发现什么都阻断。这样开发很快就会绕过它，Gate 会变成阻碍交付的摆设。

另一个极端是 AI 永远只建议。这样大家也会慢慢不看它，Review 会退化成一份没人处理的“友好提醒”。

真正有效的质量门禁，必须分层。

该拦的拦。

该问人的问人。

该提示的提示。

## 一个 Pre-PR Gate 配置长什么样？

Pre-PR Gate 不应该写死在代码里。

不同团队、不同项目、不同阶段，对风险的接受程度是不一样的。

核心支付链路和内部运营后台，不应该使用完全一样的阻断策略。

基础工具库和活动页临时代码，也不应该用同一种 Review 强度。

所以 Gate Policy 最好是可配置的。

一个简化版配置可以长这样：

```yaml
prePrGate:
  strategyId: quality-gate
  targetBranch: main
  reviewMode: AGENT
  agents:
    - role: SECURITY_AUDITOR
      skills:
        - SecuritySkill
    - role: PERFORMANCE_ANALYST
      skills:
        - PerformanceSkill
    - role: ARCHITECT_REVIEWER
      skills:
        - JavaCodeStyleSkill
        - ExceptionHandlingSkill
  gatePolicy:
    blockOn:
      - BLOCKER
    requireHumanReviewOn:
      - MAJOR
    advisoryOn:
      - MINOR
      - INFO
  output:
    generatePrSummary: true
    groupFindingsBySeverity: true
    requireEvidence: true
```

这里面有几个关键点。

第一，策略和场景绑定。

不是所有变更都需要最重的策略。小改动可以快速扫描，核心链路可以走多 Agent 质量门禁。

第二，角色和 Skill 绑定。

不同 Agent 负责不同视角，避免一个模型用同一种思路看所有问题。

第三，Gate Policy 明确。

哪些问题阻断，哪些问题需要人工确认，哪些问题只是建议，必须写清楚。否则系统状态会变得很暧昧，开发不知道该修什么，Reviewer 也不知道该信什么。

第四，输出必须有证据。

AI 不能只说“这里可能有风险”。它要说明证据在哪里、影响是什么、建议怎么修。最好还能标出文件、行号、触发规则、置信度和建议动作。

这也是 Gate 和普通聊天式 Review 的差别。

普通 Review 只是在“说建议”。

Gate 必须能进入流程，能影响状态，能被复盘。

## Finding 要能进入工程流程

Pre-PR Gate 的输出，不能只是一段漂亮的 Markdown。

它必须能进入工程流程。

所以每个问题最好都被结构化成 Finding。

例如：

```json
{
  "file": "CouponApplicationService.java",
  "line": 42,
  "severity": "BLOCKER",
  "category": "CONCURRENCY",
  "title": "库存扣减存在并发超卖风险",
  "evidence": "当前实现先查询库存再更新库存，缺少原子扣减条件",
  "suggestion": "使用条件更新：update coupon set stock = stock - 1 where id = ? and stock > 0，并检查影响行数",
  "gateAction": "BLOCK",
  "humanStatus": "PENDING"
}
```

结构化之后，系统才可以继续做很多事情：

- 在页面上按严重等级展示。
- 自动生成阻断原因。
- 把同类问题聚合。
- 让开发标记已修复。
- 让 Reviewer 确认或驳回。
- 把高频问题沉淀成规则。
- 统计 AI Review 的命中率和误报率。

如果输出只是自然语言，它很难沉淀。

如果输出是 Finding，它就可以成为治理数据。

这也是 Review Agent 平台和普通“调用一次模型”的区别。

调用模型，只是得到一次回答。

沉淀 Finding，才是在积累一套可复用的治理系统。

## AI 可以阻断基础风险，但不能独裁

Pre-PR Gate 里最容易踩的坑，是把 AI 当成最终裁判。

这会带来两个问题。

第一，AI 会误报。

它可能把可以接受的技术取舍判断成风险。

第二，AI 不知道全部业务背景。

有些变更在通用最佳实践里不完美，但在当前阶段是合理的。

所以 Pre-PR Gate 的正确姿势不是：

> AI 说不行，就绝对不行。

而是：

> AI 负责发现风险和执行硬规则，人负责最终治理权。

这也是为什么我会把 MAJOR 设计成“需要人工复核”，而不是默认阻断。

对于明确违反硬规则的问题，比如明文密钥、核心链路数据不一致、破坏团队强约束，可以直接 BLOCK。

但对于架构边界争议、测试覆盖不足、异常分支是否需要补齐这类问题，最好交给人确认。

一个成熟的 Gate 机制，应该支持例外放行。

但例外放行不能是“点一下跳过”。

它至少应该记录：

```yaml
exception:
  findingId: F-20260604-001
  decision: ACCEPT_RISK
  reason: "该接口仅用于内部灰度工具，本次先接受日志上下文不足问题，下个迭代统一补齐"
  decidedBy: "reviewer-a"
  expiresAt: "2026-07-01"
```

例外不是漏洞。

没有记录的例外才是漏洞。

好的 Gate，不是让 AI 独裁。

好的 Gate，是让风险暴露得更早、解释得更清楚、决策过程更可追踪。

## Pre-PR Gate 的真正价值

Pre-PR Gate 的价值，不是多加一道流程。

它真正解决的是三个问题。

第一，把基础问题前置。

不要等正式 PR 才发现低级错误。开发在提交前就可以自查、自修、自解释。

第二，降低人工 Review 的认知负担。

Reviewer 拿到的不是原始 diff，而是已经经过 AI 扫描、风险分级、摘要整理的变更。

第三，把团队经验变成默认执行。

规则、Skill、Gate Policy、Finding 数据会逐渐沉淀下来，变成团队自己的工程治理资产。

换句话说，Pre-PR Gate 不是为了“卡住开发”。

它是为了让真正应该进入人工 Review 的代码，更干净、更清楚、更有上下文。

好的 Gate 应该让低风险变更更快通过，让高风险变更更早暴露。

这才是质量门禁的意义。

## 结尾

AI Coding 之后，代码产出速度已经被放大。

如果 Review 仍然只发生在正式 PR 之后，团队就会不断把基础风险推迟到协作链路里处理。

这会让 Reviewer 变累，让反馈变慢，也让系统风险更难控制。

Pre-PR Gate 的价值，就是把 AI Review 前置到提交之前。

让机器先过滤机器擅长的问题。

让人保留最终判断权。

让正式 PR 从“请帮我找问题”，变成：

> 这是我已经自查过、带着风险说明和上下文的变更。

这一步做好之后，我们才有资格继续讨论下一件事：

> 一个模型够不够？为什么多模型 Review 会成为 Agent 工程化里的关键能力？
